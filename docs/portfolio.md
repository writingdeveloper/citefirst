# citefirst — 실측 기록

> 이 문서의 모든 수치는 **실제로 실행한 결과**다. 추정치·기대치는 들어 있지 않다.
> 측정하지 못한 항목은 "미측정"이라고 쓴다 (AGENTS.md §1).
>
> 측정 환경: PostgreSQL 17.10 + pgvector 0.8.5 (WSL2 Ubuntu 24.04), Node 22.16,
> 임베딩·리랭킹은 로컬 CPU 추론. 최종 측정 2026-07-29 (질문 46개).
>
> 과거 시점의 수치가 함께 실린 절이 있다(하이브리드 검토, 튜닝 이력). 비교를 위해 남긴
> 것이며 **어느 시점 어느 질문 세트인지 각 표에 적어두었다.** 현행 수치와 섞어 읽지 말 것.

## 무엇을 만들었나

PostgreSQL 17 공식 문서에 답하는 RAG 시스템. 문서 파싱 → 청킹 → 임베딩 → pgvector 검색 →
크로스 인코더 리랭킹 → 인용 달린 답변, 그리고 그 품질을 재는 평가 하네스.

**임베딩과 리랭킹이 로컬에서 돈다.** ingest 와 검색은 외부 호출이 전혀 없다.
관리형 임베딩 API 를 쓰면 클라이언트 문서 전체가 제3자 서버를 거치는데, 계약서·내부 정책을
다루는 곳에서는 그 지점에서 대화가 끝난다.

## 왜 PostgreSQL 문서인가

**정답 라벨을 실행으로 검증할 수 있기 때문이다.** 평가의 최대 약점은 "정답이 정말 정답인가"인데,
이 코퍼스는 시스템이 돌고 있는 데이터베이스 자신의 매뉴얼이라 `SHOW`, `pg_settings`,
실제 명령 실행으로 확인할 수 있다.

**46개 질문의 정답을 전부 그렇게 확인했다.** 조회로 안 되는 것은 실험을 설계했다.

⚠️ **다만 `SHOW` 를 그대로 쓰면 안 된다.** `pg_settings.setting` 은 *지금 돌고 있는 값*이라
배포판 패키지의 `postgresql.conf` 오버라이드가 섞인다. 이 인스턴스(Debian/Ubuntu 패키지)에서
실측하면 `ssl` 은 실행값 `on` 인데 **문서상 기본값은 `off`** 이고, `log_line_prefix` 도
`%m [%p] %q%u@%d ` vs `%m [%p] ` 로 다르다. 그대로 라벨로 박으면 **매뉴얼과 다른 값을
정답이라고 채점**하게 된다. 그래서 설정 기본값은 전부 `boot_val` 로 확인했다.
(먼저 만든 26개도 재점검했다 — `postgresql.conf` 에 걸린 건 `shared_buffers` 와
`max_connections` 둘뿐이고 둘 다 `boot_val` 과 값이 같아 영향이 없었다.)

- `effective_cache_size` 가 메모리를 할당하지 않는다 → 설정값 4GB 인데
  `pg_shmem_allocations` 합계는 **142.9MB**
- 실패한 `CREATE INDEX CONCURRENTLY` 가 남기는 것 → 중복 값에 unique 인덱스를 걸어 실패시킨 뒤
  `pg_index` 조회 → `indisvalid=false` 인덱스가 실제로 남음
- `VACUUM FULL` 의 락 → 3백만 행 테이블에서 실행 중 다른 세션이 `pg_locks` 관찰 →
  `AccessExclusiveLock` (작은 테이블에서는 너무 빨리 끝나 관찰되지 않는다)
- `lock_timeout` vs `statement_timeout` → 락 경합이 없을 때 `lock_timeout` 은 발동하지 않고,
  다른 세션이 `ACCESS EXCLUSIVE` 를 쥔 상태에서만 발동하는 것까지 재현

각 질문의 `verified_by` 필드에 실제로 친 명령이 들어 있다. 검증 못 한 질문이 하나라도 있으면
평가 하네스가 **실행을 거부한다** — "나중에 확인하자"가 그대로 포트폴리오 숫자가 되는 경로를
코드로 막았다.

| 항목 | 값 |

| 범위 | Server Administration · SQL Commands · Client/Server Applications · Configuration |
| 청크 | **5,012개** |
| 실패 | **0건** |
| 소요 | **550초** (약 9분, CPU 임베딩 포함) |
| 청크 크기 | 512 토큰 예산 / 오버랩 64 · 실측 중앙값 56, 평균 113, 최대 **513** |

청크 크기 분포는 파서 결함 3개를 고친 뒤의 값이다. 고치기 전에는 **137개가 512 토큰을 넘었고
최대 8,060 토큰**이었다 — 임베딩 모델 상한이 512 라 그 뒤는 조용히 잘려 있었다.
경위는 [`decisions.md`](decisions.md) D14.

## 검색 품질

`recall@5` = 정답 청크가 상위 5개에 들어온 비율. `MRR@10` = 첫 정답의 순위 역수.
후보 20개를 벡터 검색으로 뽑아 크로스 인코더로 10개까지 재정렬한다.

**질문 46개**(증상 표현 / 식별자 표현 각각), 전부 실행으로 정답을 확인했다.

### 기법을 하나씩 쌓았을 때 — 증상 표현 46문항

| 구성 | recall@5 | MRR@10 | 혼동 recall@5 |
|---|---|---|---|
| 벡터 검색만 | 0.652 | 0.467 | 0.684 |
| \+ 크로스 인코더 리랭킹 | 0.826 | 0.544 | 0.868 |
| \+ 쿼리 재작성 | 0.913 | 0.619 | 0.974 |
| \+ 리랭커에도 재작성 질의 전달 (**출시 구성**) | **0.978** | **0.834** | **1.000** |

마지막 줄이 이 프로젝트에서 가장 값이 나가는 발견이다.

> **2·3행은 한 번 올랐다.** 처음 측정에서는 0.783 / 0.848 이었는데, 리랭커에 넣는 문서
> 텍스트에 **문서 제목이 빠져 있던 것**을 뒤늦게 찾아 고친 뒤 0.826 / 0.913 이 됐다.
> 같은 문서의 첫 줄에 적은 "벡터 검색만" 행은 리랭킹을 끈 조건이라 소수점 네 자리까지
> 그대로다 — 그게 이 재측정의 대조군이다. 전말은 [`decisions.md`](decisions.md) D19.

### 리랭킹이 방금 찾아낸 답을 도로 밀어낼 수 있다

쿼리 재작성은 질문을 LLM 에 주고 **문서가 쓸 법한 낱말**을 받아 그것들로도 검색한다:

```
"Does routine table cleanup get the same memory budget as an ordinary query?"
  → maintenance_work_mem memory for VACUUM and maintenance operations default setting
  → work_mem versus maintenance_work_mem resource consumption
  → autovacuum_work_mem memory budget for autovacuum workers default setting
```

이게 잘 듣는다. 재작성을 켜고 **리랭킹을 아예 끄면** recall@5 가 0.957 이다.

그 상태에서 리랭킹을 기본 설정으로 켜면 **0.913 으로 떨어진다.** 후보 목록 안에 답이 들어 있는
3문항이 top-5 밖으로 밀려났다.

원인은 리랭커가 여전히 **원문**으로 점수를 매기고 있었다는 것이다. `bge-reranker-base` 는
도메인 지식이 없는 작은 모델이라 "routine table cleanup" 과 `maintenance_work_mem` 을
잇지 못한다 — 임베딩 모델이 못 한 그 일을 리랭커도 못 한다. 그래서 재작성이 애써 찾아낸 청크를
"질문과 안 닮았다"며 도로 내린다.

리랭커에 확장 질의(원문 + 재작성문)를 주면 **0.978** 이 된다. 리랭킹은 여전히 값을 한다 —
**같은 다리를 건너게 해줬을 때만** 그렇다.

| 리랭킹 (재작성 ON, 후보 동일) | recall@5 | MRR@10 |
|---|---|---|
| 끔 | 0.957 | 0.778 |
| 켬 · 원문으로 채점 | 0.913 | 0.619 |
| 켬 · 확장 질의로 채점 | **0.978** | **0.834** |

세 줄은 **완전히 같은 후보**를 봤다. 재작성 결과를 파일에 얼려 커밋했기 때문에 재현되고,
달라진 건 리랭커의 입력 하나뿐이다.

> **이 손실은 처음에 두 배로 측정됐다.** 원래 표는 0.848(6문항)이었다. 그중 절반은 리랭크
> 질의 탓이 아니라 **리랭커 입력에 문서 제목이 없던 탓**이었고, 그걸 고치니 0.913(3문항)이
> 됐다. 결론(`expanded` 가 맞다)은 그대로지만 **크기는 절반이다.** 두 원인이 같은 방향으로
> 겹쳐 있었고, 하나를 찾기 전에는 다른 하나가 전부인 줄 알았다 — D19.

**기법을 하나씩 켜고 끄는 측정만 하면 이걸 놓친다.** "재작성 ON/OFF" 표만 보면 어느 쪽이든
개선으로 보인다. 손해는 기법 **사이**에서 났다.

### 같은 사실을 두 가지 방식으로 물었을 때

| 질문 방식 | 리랭킹 (recall@5) | 쿼리 재작성 (recall@5) |
|---|---|---|
| **증상으로 물음** | 0.652 → **0.826** ✅ | 0.826 → **0.978** ✅ |
| **정확한 파라미터 이름을 씀** | 0.978 → 0.978 (변화 없음) | 0.978 → 0.978 (변화 없음) |

`work_mem` 이라는 이름을 아는 사람은 애초에 검색이 필요 없다. 매뉴얼을 뒤지는 사람은
증상으로 묻는다 — *"정렬하다가 디스크로 새는데 어느 설정이죠?"* 두 기법 다 **거기서만** 값을 한다.
식별자로 묻는 질문에서 재작성은 질의당 3.3초와 630토큰을 쓰고 아무것도 얻지 못한다.

### 26문항에서 냈던 결론 하나가 46문항에서 뒤집혔다

질문이 26개였을 때 이 문서는 "식별자 질문에서는 리랭킹이 MRR 을 **낮춘다**"고 적었다
(0.839 → 0.804). 46개에서는 반대로 **올린다**(0.823 → **0.867**).

그때는 "대신 recall@5 가 조금 떨어진다(0.978 → 0.957)"고 덧붙였다. **그것도 틀렸다.**
그 손실은 표본 문제가 아니라 **버그**였다 — 리랭커에 넣는 텍스트에 문서 제목이 없어서
같은 정의가 어느 문서 것인지 구분하지 못했다. 고친 뒤에는 0.978 → **0.978**, 손실이 0 이다.

한 절에서 결론이 두 번 뒤집혔다. 옛 문장을 조용히 고치지 않고 남겨두는 이유가 이것이다 —
아래 "남은 한계"의 *"세 번째 소수점은 노이즈"* 는 추상적인 경고가 아니고, **"지표가 떨어지면
표본을 의심하기 전에 파이프라인을 의심해야 한다"** 는 것도 같이 배운 것이다 (D19).

### 순위가 뒤집히는 실제 사례

*"A query keeps spilling sorts to disk. Which setting limits that memory?"*

| 청크 | 벡터 거리 (작을수록 유사) | 리랭커 점수 |
|---|---|---|
| `work_mem` ← **정답** | 0.3493 (2위) | **1.83 (1위)** |
| `temp_file_limit` | **0.3261 (1위)** | −0.98 |
| 임시 정렬 파일 관련 Notes | 0.3820 (3위) | −1.18 |

벡터 검색은 `temp_file_limit` 을 1위로 뽑았다. 질문에 "disk", "temporary", "sort" 가 다 들어 있고
그 문서에도 똑같이 들어 있으니 당연한 결과다. 하지만 사용자가 원한 건 **메모리 한도**이지
디스크 한도가 아니다.

크로스 인코더는 질문과 문단을 **같이** 읽기 때문에 그 차이를 잡아낸다. 점수 간격도 넓다
(1.83 vs −0.98). 이게 "chunking, embedding, reranking 이 답의 정확도를 가른다"는 주장의 실물이다.

## 튜닝: 무엇을 고쳤고 얼마나 올랐나

측정 → 실패 분석 → 수정 → 재측정으로 얻은 것들이다. **효과 열의 수치는 그 수정을 했던 시점의
질문 세트로 잰 값이다** — 앞의 다섯 줄은 질문 26개 시점, 뒤의 다섯 줄은 46개 시점이다.
현행 수치와 섞어 읽지 않도록 원래 값을 그대로 둔다.

| 수정 | 근거 | 효과 |
|---|---|---|
| `<dt>` 를 헤딩으로 승격 | `<dl>` 을 통째로 삼켜 `work_mem`/`maintenance_work_mem` 설명이 한 덩어리가 되고 예산에 따라 임의로 잘렸다 | 파라미터별로 청크 분리 |
| 헤딩 경계에서 오버랩 차단 | `maintenance_work_mem` 헤딩 청크가 `hash_mem_multiplier` 내용으로 시작했다 | 헤딩과 내용의 불일치 제거 |
| **임베딩 텍스트에 문서 제목 추가** | SQL 명령 페이지는 헤딩이 "Notes" 뿐이라 **VACUUM 청크의 벡터에 "VACUUM" 이라는 단어가 없었다** | recall@5 0.769 → **0.808**, 실패 6 → 5건 |
| 소스 줄바꿈 정규화 | `ACCESS\n   EXCLUSIVE` 가 텍스트에 그대로 남아 검색이 빗나갔다 | 라벨 검사 22/26 → **26/26** |
| 청크 예산 계산 수정 | 오버랩 자리를 빼지 않아 512 예산에 최대 620 토큰이 나왔다 | 예산 초과 **0건** (최대 502) |
| 네비게이션 제거 | 페이지마다 반복되는 "Prev/Up/Next" 가 모든 청크에 섞였다 | 벡터 오염 제거 |
| **쿼리 재작성** | 어휘 격차는 검색기를 더 붙여서는 못 넘는다. 질문의 낱말 자체를 바꿔야 한다 | recall@5 0.826 → **0.978** |
| **리랭커에도 확장 질의** | 재작성이 찾아낸 3문항을 리랭커가 도로 밀어냈다 | recall@5 0.913 → **0.978** |
| **리랭커 입력에 문서 제목 추가** | 리랭커가 `pg_dump` 의 정의와 `pg_basebackup` 의 **같은 정의**를 구분할 정보를 못 받고 있었다. 임베딩 쪽은 진작 넣고 있었다 | 사다리 2·3행 0.783 → **0.826** · 0.848 → **0.913**, 식별자 세트의 리랭킹 recall 손실 −0.021 → **0** |
| `<pre>` 마크업 유출 차단 | 청크 본문에 `<code class="prompt">` 가 그대로 들어가 인용 화면에도 보였다 | 오염 청크 **384 → 0** |
| 문장 경계 없는 블록 강제 분할 | 137개 청크가 임베딩 상한(512토큰)을 넘어 **뒤쪽이 조용히 잘려** 검색에 도달하지 못했다 | 초과 **137 → 1**, 최대 8,060 → 513 |
| 오버랩 길이 상한 | 문장 경계가 없으면 직전 청크를 **통째로** 복사해 중복 청크가 생겼다 | 중복 제거 |

아래 세 줄(파서·청커 결함)은 **eval 이 잡아준 게 아니다.** 발견 당시 지표는 recall@5 1.000 /
인용 유효성 1.000 이었다. 새 정답 라벨을 만들며 청크 본문을 눈으로 읽다가 나왔다.
경위는 [`decisions.md`](decisions.md) D14 — 이 하네스가 무엇을 못 보는지의 기록이기도 하다.

## 하이브리드 검색을 붙였다가 껐다 — 측정이 시킨 일

남은 실패가 전부 어휘 격차였으니 키워드 검색을 섞으면 나아질 것이라 보고,
Postgres FTS(`tsvector` + GIN)를 붙여 벡터 검색과 RRF 로 합쳤다. 임베딩은 다시 만들지 않았다 —
`tsvector` 는 이미 저장된 `content` 로 계산된다.

**결과는 기대와 반대였다.** (아래는 **질문 26개 · 재작성 도입 전** 시점의 측정이다.
같은 조건을 46개에서 다시 잰 값은 이 절 끝에 있다.)

| 지표 (리랭킹 ON, 증상으로 묻는 질문, 26문항) | 하이브리드 OFF | 하이브리드 ON |
|---|---|---|
| recall@5 | 0.808 | 0.808 |
| MRR@10 | **0.556** | 0.551 |
| recall@5 (혼동 질문만) | **0.895** | 0.842 |

질문에 `VACUUM` 이라는 단어가 없으면 **키워드 검색도 그 문서를 못 찾는다.** BM25 계열은
어휘 격차를 메우기는커녕 어휘 일치에 더 의존한다. 대신 엉뚱한 문서를 상위로 올려
RRF 에서 좋은 벡터 후보를 밀어냈다 — 혼동 질문의 −0.053 이 그 밀어내기다.

반대로 **정확한 식별자를 쓰는 질문**에서는 MRR@10 이 0.804 → **0.821** 로 올랐다.

### 후일담 — 쿼리 재작성이 하이브리드가 진 원인을 없앴다

하이브리드가 진 이유는 어휘 격차였다. 질문에 식별자가 없으니 키워드 검색이 엉뚱한 문서를
올려 좋은 벡터 후보를 밀어냈다. 그런데 **재작성문에는 식별자가 들어 있다.** 그래서 재작성을
켠 상태에서는 키워드 검색도 제 문서를 찾고, 하이브리드가 더는 해롭지 않다:

| 증상 표현 46문항, 재작성 ON | 하이브리드 OFF | 하이브리드 ON |
|---|---|---|
| recall@5 | 0.978 | 0.978 |
| MRR@10 | 0.834 | 0.849 |

**그래도 기본값은 계속 OFF 다.** recall@5 는 같고, MRR +0.012 는 46문항에서 한 문항이
한 칸 오르내리는 폭이다. 질의 4개마다 FTS 질의를 하나씩 더 붙일 값어치가 없다.
**원인이 사라졌다는 게 곧 켤 이유는 아니다.**

**코드는 남기고 기본값만 껐다**(`HYBRID_ENABLED=false`). 스위치 자체가 산출물이다 —
클라이언트 코퍼스에서 다시 재보고 켤지 정하면 된다. 측정 없이 켰다면
성능을 떨어뜨리고도 몰랐을 것이고, 그게 이 레포가 증명하려는 지점이다.

## 남은 검색 실패 1건 — 지우지 않는다

출시 구성(재작성 ON · 리랭커에 확장 질의) 기준, 46문항 중 1건이다.

**q012** — *"포맷 옵션 없이 덤프하면 무슨 파일이 나오나?"*
재작성은 완벽했다(`pg_dump default output format`). 정답 문서도 찾았다. 그런데 정답 청크의
**본문 전체**가 이것뿐이다:

> "Output a plain-text SQL script file (the default)."

대신 부모 청크가 3위로 올라온다 — *"Selects the format of the output. format can be one of
the following:"* — 목록을 소개할 뿐 답이 없는 문단이다.

**이건 버그가 아니라 트레이드오프다.** `<dt>` 를 헤딩으로 승격하는 규칙이 `work_mem` 과
`maintenance_work_mem` 이 한 청크로 섞이는 걸 막았고, 혼동 질문 recall 1.000 의 근거가
바로 그 규칙이다. 그런데 정의가 한 줄이면 **검색되기엔 너무 작은 청크**가 된다.
짧은 정의를 부모에 되붙이면 그 분리가 깨질 위험이 있다 — 별도 측정 사이클이 필요하고,
그때까지 이 실패를 남겨둔다.

## 답변 품질

46개 질문 전부에 대해 실제로 답변을 생성하고 judge 로 채점했다 (출시 구성).

| 지표 | 리랭킹 OFF | 리랭킹 ON |
|---|---|---|
| citation validity | **1.000** | **1.000** |
| grounded (검색된 근거만으로 뒷받침되는가) | 0.978 ~ **1.000** | 0.978 ~ **1.000** |
| correct (실행으로 확인한 정답과 일치) | 0.978 ~ **1.000** | 0.957 ~ 0.978 |

> **아래 두 줄을 범위로 적은 이유.** `citation validity` 는 코드가 대조하므로 흔들리지
> 않는다. `grounded`·`correct` 는 judge 판정이고, **입력이 완전히 같아도 뒤집히는 경우가
> 있다.** 짝지어 비교한 약 138문항 중 3건이 그랬다(46문항 기준 1~2문항 = 0.02).
> 같은 설정을 두 번 돌려 전부 일치한 쌍도 있으니 대체로 재현되기는 한다 — 다만 보장되지
> 않으므로 **점추정 하나로 싣지 않는다.** 상세는 [`decisions.md`](decisions.md) D19.

**citation validity 1.000 — 두 조건 합쳐 인용 170건, 환각 0건.** 모델이 뱉은 인용 ID 를
서버에서 실제 청크와 대조해 매칭 실패한 것만 걸러내는데, 걸러낼 게 없었다. 이 시스템이 주장하는
*"확인할 수 있는 인용"* 이 이 숫자다.

**근거 없이 지어낸 답이 한 건도 없었다.** 이게 더 중요하다.
오답이던 q012 에 대한 judge 판정문이 그 이유를 그대로 말해준다:

> *"The excerpts do not state pg_dump's default format, so the answer is grounded in them,
> but it conflicts with the verified default of a plain-text SQL script."*

**모델은 `pg_dump` 의 기본 포맷을 알고 있다.** 그런데 발췌에 없으니 없다고 말했다.
검색 실패가 오답이 되는 건 어쩔 수 없지만, **검색 실패가 환각이 되지는 않았다.**

> **후일담 — 이 답변이 버그를 진단해줬다.** 같은 질문의 답변 본문은 더 구체적이었다:
> *"The 'plain' default shown applies to `pg_basebackup`, not `pg_dump`."* 모델은 **틀린
> 문서의 청크를 받았다는 것까지** 말한 것이다. 리랭커가 `pg_basebackup` 의 `p plain`(126토큰)을
> `pg_dump` 의 것(13토큰)보다 위에 올렸기 때문이고, 원인은 리랭커 입력에 문서 제목이 없던
> 것이었다. 고친 뒤 q012 는 `[c10597]` 을 인용해 맞게 답한다. **판정문을 읽지 않고 지표만
> 봤기 때문에 원인을 한동안 놓쳤다** — D19.
RAG 시스템에서 실무적으로 가장 중요한 성질이고, judge 를 "답이 사실인가"가 아니라
"발췌만으로 뒷받침되는가"로 채점하게 설계했기 때문에 이 구분이 수치로 나온다.

judge 는 답변 생성과 같은 모델을 쓴다 — 자기 채점 편향이 있을 수 있다. 다만 `correct` 는
**실행으로 확인한 참조 답안**과 대조하는 것이라 모델의 의견이 아니라 사실 대조에 가깝다.

### 리랭킹은 검색을 올리고 답을 하나 깎았다 — 그리고 그게 단서였다

`correct` 열은 리랭킹 OFF 가 ON 보다 **높다.** 좋은 쪽 열만 싣지 않는다.

리랭킹 OFF 에서는 recall@5 실패가 2건(q035·q044)인데 `correct` 는 그보다 높다 — 라벨이
인정하지 않은 다른 청크로도 답이 나왔다는 뜻이다. ON 에서는 검색 실패가 q012 하나로 줄었지만
그 하나가 답까지 틀렸다.

**이 한 줄이 남은 실패의 원인을 가리키고 있었다.** `correct` 가 리랭킹으로 *내려가는* 유일한
지표이고, 뒤집히는 질문이 q012 하나라면, q012 를 틀리게 만든 것은 리랭킹이다. 그런데도 이
문서는 한동안 q012 를 "짧은 정의 청크라 검색이 안 된다"로 적고 있었다. 실제로는 벡터 검색이
그 청크를 **1위로** 찾아냈다 (D19).

### recall@5 는 실제보다 박하게 나온다

위가 그 사례다. `recall@5 = 0` 인데 **답은 맞은** 경우가 리랭킹 OFF 에서만 2건이었다.
정답을 담은 청크가 코퍼스에 여럿인데 라벨은 그중 하나만 정답으로 인정하기 때문이다.

그래서 `recall@5` 는 **검색 시스템의 하한**으로 읽어야 한다. 라벨을 느슨하게 하면 숫자는
오르지만 의미가 흐려지므로, 박한 쪽을 택하고 이 한계를 적어둔다.

## 쿼리 재작성의 대가 — 그리고 이 수치를 그대로 옮기면 안 되는 이유

| | |
|---|---|
| 지연시간 | 질의당 **평균 4,066ms** (최대 12,648ms). 임베딩+벡터검색은 약 200ms 다 |
| 토큰 | 질문당 입력 약 630 · 출력 약 50 |
| 실패 | 46문항 중 **0건** (파싱 실패 시 원문만으로 검색하고 `rewriteFailed` 로 보고한다) |

지연시간이 압도적으로 크다. 대화형 UI 라면 재작성 진행을 화면에 보여주며 스트리밍해야 하고,
같은 질문이 반복되는 워크로드라면 캐시가 사실상 필수다.

### 이 +0.195 의 일부는 검색이 아니라 모델의 사전지식이다

재작성 모델은 **PostgreSQL 을 이미 안다.** "sorts spilling to disk" → `work_mem` 은
검색이 아니라 학습 데이터에서 꺼내온 것이다. 그러니 이 이득을 "검색기가 좋아졌다"로 읽으면 안 되고
**"질의 앞단에 도메인 지식을 하나 붙였다"**로 읽어야 한다.

운영에서도 같은 모델을 쓸 수 있으니 실용적으로는 유효하다. 하지만 **모델이 본 적 없는 사내
문서**(내부 정책, 자사 제품 용어)가 코퍼스라면 이 효과는 줄어든다. 그 코퍼스에서는 재작성
프롬프트에 용어집(약어·제품명 대응표)을 넣어줘야 같은 일을 한다.

**여기 적힌 수치 중 다른 코퍼스로 옮겨갈 가능성이 가장 낮은 게 이것이다.** 클라이언트에게
그대로 인용하지 않는다.

### 재작성은 결정적이지 않다 — 그래서 얼려서 커밋한다

질문 26개 시점에 같은 설정으로 두 번 돌렸더니 recall@5 가 **0.962 와 1.000** 으로 갈렸다.
설정은 하나도 안 바뀌었고 달라진 건 그날 모델이 뽑은 재작성문뿐이었다.

그 상태로는 "확장 질의가 원문보다 낫다"의 일부가 잡음이다. 그래서 재작성 결과를
`eval/rewrite-cache.json` 에 얼려 **커밋한다.** 최초 호출의 지연시간·토큰도 함께 적어서
비용을 나중에도 추정치가 아니라 실측값으로 인용할 수 있게 했다.

이 파일을 지우면 재작성이 새로 뽑히고 **위 표가 재현되지 않는다.** 지웠다면 표를 다시 내야 한다.

## 측정에 쓴 모델

**답변·judge = `gpt-5.6-sol`** (Codex 구독, 로컬 CLIProxyAPI 경유). 수치는 전부 이 모델로 낸 것이다 —
숫자는 그것을 만든 모델과 함께 읽어야 의미가 있다.

답변 계층은 **Anthropic Messages 프로토콜**을 말하고 `ANTHROPIC_BASE_URL` 로 백엔드를 바꾼다.
코드는 provider 에 묶여 있지 않다.

**이건 우회가 아니라 설계다.** RAG 시스템에서 납품 후 가장 자주 바뀌는 부분이 모델이다 —
클라이언트가 벤더를 갈아타거나, 구독이 끝나거나, 컴플라이언스 심사에서 특정 provider 가
배제된다. 검색 품질을 결정하는 것들(파싱·청킹·임베딩·리랭킹·인용 검증)은 전부 그 선 아래에
있어서 영향을 받지 않는다. 모델을 바꿔도 **이 문서의 방법론과 하네스는 그대로 쓸 수 있다.**

**프록시 경유 시 주의:** `output_config.format.json_schema` 가 **에러 없이 무시된다.**
judge 를 스키마에 의존하지 않게 짠 이유다. 프롬프트 캐싱도 실제로는 걸리지 않는다
(`cache_read_input_tokens = 0`) — 비용 계산에서 캐시를 전제하지 않는다.
